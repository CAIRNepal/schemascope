# Decisions

SchemaScope began as a copy of NeuroSchema (neuroschema.org); see that repository's DECISIONS.md for D-001–D-015, which still apply: static build, FAIR + quality rubric, provenance and run archive, Git-based submissions, local evaluation.

## S-001: Cross-domain fork of NeuroSchema   (2026-10-25, status: accepted)
**Context** – The owner wants the same catalog and evaluation for every domain, not only neuroscience.
**Decision** – SchemaScope reuses the NeuroSchema code with its own brand: the SchemaScope logo, a navy/teal/blue/amber palette and its own domain list. Records have a primary domain plus secondary `domains`, which the landing page uses for a cross-domain map and "strongest bridges". The landing page shows only highlights, and the full catalog is paginated.
**Why** – One codebase, proven scoring, and less to maintain. Rejected: one site with a neuroscience filter, because NeuroSchema keeps its own curated depth and audience.

## S-002: Exhaustive coverage by harvesting registries   (2026-10-25, status: accepted)
**Context** – Hand-curation can't reach thousands of ontologies.
**Decision** – `scripts/harvest.py` harvests Bioregistry (semantic artefacts only), OBO Foundry, OLS, TIB, LOV and NeuroSchema, and merges records by prefix, cross-mappings, IRI, and same name on the same host. Domains come from the registries' own subject labels plus keyword rules. Each record keeps per-field provenance (registry, URL, time). `data/sources.json` and `data/sources/*.gz` archive every download, so `--offline` rebuilds are reproducible. Curated values in `data/curated.json` win over registry values.
**Why** – Registries are maintained by their communities, and combining them gives breadth plus cross-checks. Rejected: scraping web pages, which is fragile, and copying a single registry, which leaves gaps (e.g. LOV covers semantic-web vocabularies that biomedical registries don't).
**Consequences** – BioPortal, AgroPortal, MatPortal, IndustryPortal and other OntoPortal instances need API keys and will be added as sources once keys are configured. FAIRsharing needs a login.

## S-003: Discovery by dereferencing   (2026-10-25, status: accepted)
**Context** – Many ontologies (privacy, security, CS, manufacturing, project ontologies such as smashHitCore) are in no registry.
**Decision** – `scripts/discover.py` takes candidates from prefix.cc, w3id.org, Zenodo, GitHub topics (with a token) and `data/candidates.txt` (e.g. from papers, with the DOI). It requests RDF and accepts only artefacts that declare an ontology or vocabulary with a title and ≥ 5 terms. Metadata is read from the artefact itself, ignoring titles that merged-in W3C vocabularies leave behind. Probe results are cached for 30 days.
**Why** – Content negotiation tells us objectively whether something is a published ontology. Rejected: listing every namespace without checking it, which would be noisy and full of dead links.

## S-004: Privacy, Security & Law domain   (2026-10-25, status: accepted)
**Decision** – A dedicated domain for data protection, GDPR, consent, contracts, cybersecurity and legal ontologies. It is fed by LOV's Security and Contracts tags and keyword rules.

## S-005: Submissions are saved as curated entries   (2026-10-26, status: accepted)
**Context** – The submission bot (`scripts/issue-to-entry.mjs`) wrote only to `data/catalog.json`, which `scripts/harvest.py` rebuilds from the registries plus `data/curated.json`. The next harvest would have dropped every submitted entry. The bot also wrote the catalog with 2-space indentation while the harvest uses 1, so each submission PR reformatted all ~2,700 entries. And, as in NeuroSchema, the workflow only ran for issues carrying a `submission` label that didn't exist in the repo.
**Decision** – The bot writes the entry to both files. A new entry gets `provenance.source: "curated"` with `curatedAt` and `curatedBy: "submission #N"`. A correction records the submitted fields under `provenance.overrides`, which the harvest applies on top of registry values. Submitter-supplied `provenance` is ignored. Both files keep the harvest's formatting. The workflow passes `ISSUE_NUMBER`, commits `data/curated.json` too, and runs on the form's JSON field as well as the label, creating the label when missing.
**Why** – `curated.json` is already the place harvest-proof values live. Rejected: making the harvest keep every non-harvest catalog entry, which would also keep entries a registry has removed or renamed.
**Consequences** – Entries submitted before this change that aren't in `curated.json` must be copied there by hand before the next harvest.

## S-007: NeuroSchema's values win in the harvest   (2026-10-27, status: accepted)
**Context** – `scripts/harvest.py` kept the first value it found for each field, and NeuroSchema is read last. So edits made in NeuroSchema (descriptions, links, publications) didn't reach entries also listed in Bioregistry, OBO, OLS, TIB or LOV. Six entries (`bids`, `nwb`, `hed`, `openminds`, `neuroml`, `dandi-schema`) were also frozen as "NeuroSchema catalog" snapshots in `data/curated.json`, which override every harvest.
**Decision** – NeuroSchema's values replace other registries' values for any field it gives. When NeuroSchema is harvested for an entry, the snapshot in `curated.json` keeps only its SchemaScope domain (category, domains). Entries curated in SchemaScope itself (`source: curated`) and their overrides still win. Harvest now lists new, updated and removed entries, with the fields that changed, and prints the `ONLY=` list to rescore.
**Why** – NeuroSchema is curated by hand and is the source of truth for neuroscience entries. Rejected: updating the snapshots in `curated.json` by hand after each NeuroSchema change, which is easy to forget.
**Consequences** – About 30 shared entries (e.g. `cl`, `uberon`, `go`) now show NeuroSchema's name/description/links instead of Bioregistry's. The six snapshots in `curated.json` are now only fallbacks and could be deleted later. Rescore changed entries after a harvest.

## S-008: Run ROBOT on every ontology; the OBO Dashboard is a comparison, not a source   (2026-10-27, status: accepted)
**Context** – `scripts/quality.mjs` skipped ROBOT for ontologies on the OBO Dashboard, and `scripts/rubric.mjs` took consistency, unsatisfiable classes, OWL 2 DL and the ROBOT report from the Dashboard first. So scores for OBO ontologies depended on an outside service and its schedule.
**Decision** – ROBOT (report → ELK reason → DL profile) runs on every ontology. The rubric (now 3.5) uses our result first, and the Dashboard's only when ours is missing. Each result stores `dashboardComparison`, which lists each check side by side. The ontology page shows it as "Our checks vs the OBO Dashboard", and `evaluate.mjs` prints the ontologies where the two differ. The download and Python-scan limits default to 5 GB, and files are hashed as a stream. ROBOT's Java heap is configurable (`ROBOT_HEAP`), and by default is 2 GB less than Docker's memory (4–12 GB).
**Why** – SchemaScope's scores should be reproducible from its own checks alone. Rejected: keeping the Dashboard first and only showing ours, which leaves scores tied to when the Dashboard last ran.
**Consequences** – OBO Foundry ontologies can score differently. We check the full download, which often includes imported terms, while the Dashboard usually checks the `-base` file, so ROBOT error counts can be much higher (e.g. MF: 140 vs 2). R1.3 (OBO principles) still comes from the Dashboard, since there's no local equivalent. Rebuild the ROBOT image (`docker build docker/robot`) for the configurable heap. Large ontologies need Docker Desktop's memory raised.

## S-009: Rubric v4.0, source-neutral evidence   (2026-10-27, status: accepted)
**Context** – Several v3 checks could only be scored from OBO infrastructure. F4 and A2 ignored LOV and most registries, and R1.3 used only the OBO Dashboard. Q scored 0 for checks that were never run. ROBOT errors and unsatisfiable classes cost points twice (in Q and in P). A draft proposal ("rubric v4.0 (draft): source-neutral evidence") measured the effect from stored facts.
**Decision** – F4 counts LOV, and A2 accepts any of those registries. R1.3 is the better of the OBO principle pass rate (×3) and a FAIRsharing listing (2). LOV isn't counted under R1.3, so one listing isn't counted three times. A Q check that couldn't be run (no file, too large, tool timed out) is "not assessed": it's left out of the possible points, and the grade is marked *. A file ROBOT can't load still scores 0. The ROBOT report checks (errors, warning density) apply only to OBO-style ontologies. P no longer penalises unsatisfiable classes or ROBOT errors.
**Why** – Missing evidence from a source that doesn't cover a resource isn't a failure. Rejected from the draft: counting LOV for R1.3 (triple counting), and treating unloadable files as "not assessed" (that would reward broken artefacts).
**Consequences** – From the same stored facts as v3.5, 309 grades rise and none fall. The OBO mean goes 51.9 → 56.9 and the non-OBO mean 18.7 → 24.5. One score drops by 1 point through rounding. Most ontologies are marked * until quality checks have run on them. Run `npm run rescore` (no network) or the next refresh to apply it.

## S-010: Contact page with contributors from GitHub   (2026-10-27, status: accepted)
**Context** – The site had no contact details and didn't credit contributors.
**Decision** – Add a /contact/ page with the maintainer's name, emails and website (`CONTACT_NAME`, `CONTACT_EMAILS`, `CONTACT_SITE` override them at build time). It also lists contributors from the GitHub API at build time, without bots, caching the last good list in `.local/contributors.json`.
**Why** – Contributors stay current without manual edits. Rejected: a hand-maintained list, which goes stale.
**Consequences** – The build makes one GitHub API request (it uses `GITHUB_TOKEN` if set). An offline build uses the cache, or else just links to GitHub.

## S-011: Rubric v4.1: read imports from the ontology file, and check every ontology   (2026-10-27, status: accepted)
**Context** – I3, upper-ontology alignment and RO use came only from OLS and Bioregistry import lists. Those cover few non-OBO ontologies, so most showed "no imported vocabularies found". Quality checks covered only a few dozen ontologies, because each run had a 2-hour limit and checked one ontology at a time.
**Decision** – `scripts/artefact-scan.mjs` streams each downloaded file (up to 500 MB, `ARTEFACT_SCAN_MB`) and records `owl:imports` and the vocabularies it uses (at least 3 distinct terms). OBO terms are recognised by their `PREFIX_` IRIs, and other namespaces by LOV and a short list of well-known ones. The rubric (v4.1) adds these to the OLS/Bioregistry lists for I3, upper-ontology alignment (now also GFO and gUFO) and RO. `quality.mjs` runs `QUALITY_JOBS` ontologies at a time, sharing Docker's memory between them, and prints how many ontologies have been checked. `npm run quality:all` runs it with no time limit, skipping ontologies checked in the last 30 days so it can be stopped and resumed.
**Why** – Evidence from the file itself covers every ontology. Rejected: parsing each file with rdflib, which is too slow and memory-hungry for multi-GB ontologies.
**Consequences** – The new evidence appears only after a quality run has read an ontology's file. Until then the old OLS/Bioregistry evidence is used.

## S-012: Per-criterion metrics across runs; issue templates for problems and ideas   (2026-10-27, status: accepted)
**Context** – Entry pages listed changes in score, version and term count between runs, but not which criterion or quality metric changed. The contact page linked to a blank GitHub issue.
**Decision** – Each run's history point stores per-criterion points, the penalty and the quality metrics (consistency, unsatisfiable classes, OWL 2 DL, ROBOT errors and warnings, critical pitfalls, imports, reuse). Entry pages show a "Metrics across runs" table that highlights what got better or worse, and list per-criterion changes. New issue forms, "Report a problem" and "Suggest an idea", are linked from the contact page.
**Why** – It shows whether a score moved because the resource changed or because the rubric did. Structured issues are easier to act on. Rejected: a free-text issue link.
**Consequences** – Runs archived before this change have fewer metrics, so their table cells show "—".

## S-013: Rubric validation without outside FAIR tools   (2026-10-27, status: accepted)
**Context** – The roadmap planned to validate the rubric against expert ratings and outside FAIR assessments (FOOPS!, O'FAIRe).
**Decision** – `scripts/validate-rubric.mjs` (`npm run validate:rubric`) works from stored facts, with no network:
- weight sensitivity: 1,000 random ±30% weightings with a fixed seed, plus each criterion −30%, +30% and dropped;
- agreement between our ROBOT results and the OBO Dashboard, check by check;
- agreement with expert ratings from `data/validation/expert-ratings.csv`, a 1–5 rating per resource.
It writes `data/validation/report.json`, which the site shows at /evaluation/validation/.
**Why** – FOOPS! overlaps with what the rubric already measures, and its hosted service was unavailable. O'FAIRe needs a BioPortal API key. Running either adds an outside dependency to a self-contained evaluation. Rejected: running FOOPS! locally in Docker.
**Consequences** – On the current data, rank correlation under random weights averages 0.996, 96.4% of resources keep their grade, and 133 are borderline. Dashboard agreement fills in as quality checks run. Expert ratings still need raters.

## S-014: FastAPI backend + server-rendered UI instead of a fully static site   (2026-10-31, status: superseded by S-015 for the UI part)
**Context** – `scripts/build.mjs` (1,684 lines) renders every page into `dist/` from JSON files: one HTML page and one `entry.json` per entry (2,688 entries), a client-side search index, and every archived run copied into the site. Each full run snapshot is ~16 MB and the build loads all of them into memory, so build time, memory and deploy size grow with every run and every new entry. Search and filtering run in the browser over the whole catalog.
**Decision** – Split serving into two parts, used by both SchemaScope and NeuroSchema (same code, different `site.config.json` and data):
- `backend/` – Python FastAPI service (`catalog_api`). `python -m catalog_api.ingest` loads `data/catalog.json`, `categories.json`, `evaluation.json` and `data/runs/*.json` into SQLite (`.local/catalog.db`, git-ignored) with FTS5 search; runs already loaded are skipped, so ingest stays incremental. A JSON API (`/api/...`) serves paginated search, entries, per-entry history, runs and stats.
- MCP on the same server (`/mcp/`, streamable HTTP, Python `mcp` SDK) exposes the same queries as tools (search, entry details, history, categories, stats), so agents get exactly what the API returns.
- `web/` – Next.js (App Router) UI that renders pages on the server from the API, so entry pages stay indexable. It reuses the current stylesheet and brand assets.
- Evaluation stays in Node for now: `evaluate`, `rescore`, `quality` and `rubric.mjs` still write `data/`; ingest reads their output. Rubric metadata is read from `rubric.mjs` at ingest time so the two never disagree.
**Why** – Pages, search and history are computed per request from an indexed database instead of rebuilding thousands of files; run history can grow without growing the deploy. One query layer serves the UI, third-party API users and MCP clients. Rejected: keep the static site and paginate the build (still rebuilds everything per run); a Vite single-page app (entry pages would lose server rendering and search-engine indexing); Postgres now (SQLite is enough for a read-mostly catalog of this size and needs no server; the query layer is small enough to move later); porting the evaluator to Python in the same step (large, and unrelated to serving).
**Consequences** – Deploy needs a Python process (API + MCP) and a Node process (UI) instead of static hosting; `vercel.json`/`dist/` stay until the new stack is deployed. First version covers home, catalog search (server-side, with facet counts and pagination; `/search/` redirects to it), categories, entry pages (scores, breakdown, history, metrics across runs, portals, provenance), runs/methodology summary, an API & MCP page, sitemap and robots. Pages not ported yet are proxied to the static build via `LEGACY_SITE_URL`, so links keep working during the move. URLs (`/o/<id>/`, `/category/<id>/`, `?cat=`/`?reg=` filters) are unchanged.
Notes: the MCP SDK is v2 (`MCPServer`); its endpoint rejects unknown Host headers, so production must set `MCP_ALLOWED_HOSTS`. SQLite connections are per thread (a shared one broke under concurrent requests). The UI build pre-renders some pages, so it needs the API reachable at build time. Google Tag Manager/consent is not wired into the new UI yet (no analytics until it is). Fixed in passing: a `.stat` rule for the rubric-validation grid also styled card footers on the static site.
Update (same day): content pages ported too: submit (React form, correction mode pre-filled from the API), about, contact (contributors from the GitHub API, cached a day; contact details in `site.config.json`), roadmap and rubric validation (from `data/roadmap.json` and `data/validation/report.json`, served at `/api/content/{name}`), privacy. The static site's JSON URLs (`/catalog.json`, `/o/<id>/entry.json`, `/runs/…`) redirect to the API. Helper lists moved from `/api/entries/top|recent|ids` to `/api/top-entries`, `/api/recent-entries`, `/api/entry-ids` because an entry is called `top`. `web/scripts/check-links.mjs` crawls a running site for broken links.
Follow-ups: the full methodology text, the hero illustration and the cross-domain map; DCAT `catalog.jsonld` and per-entry PROV-O from the API; analytics with consent; retire `build.mjs`; consider porting the evaluator to Python.

## S-015: The web server renders the original page templates; the Next.js UI is dropped   (2026-10-31, status: accepted)
**Context** – S-014 added a Next.js UI that re-implemented the pages in React. It differed from the static site in many small ways (missing hero illustration and cross-domain map, different catalog filters and search, different methodology page, no analytics consent), and every template change would have had to be made twice. The UI must look and behave exactly like the static site.
**Decision** – The page templates move unchanged from `scripts/build.mjs` into `scripts/site.mjs` (`createSite(data)` returns every output path with a function that renders it). `build.mjs` loads `data/` and writes `dist/` as before. `web/server.mjs` (Node, no dependencies) fetches the same data from the API (`/api/site-data`, plus `/api/runs/{id}/snapshot` for run files), renders pages on first request into a bounded cache, applies the `vercel.json` headers, and reloads when the API has ingested new data. Run history for the pages comes from the API's history table, which the ingest computes with the templates' own `historyPoint()` (run through Node), so the API and the pages agree exactly.
**Why** – One set of templates, so the server and the static build cannot drift; verified by fetching all 5,415 output files from the server and comparing them byte for byte with `dist/` (only the per-build cache-busting `?v=` differs). Rejected: keeping the React port and fixing differences one by one (never exact, double maintenance); Jinja templates in FastAPI (another re-implementation).
**Consequences** – `web/app`, `web/components`, `web/lib` and the Next.js dependencies are removed. The server holds the catalog and evaluation in memory (as the static build did), but nothing is written to disk and data updates need no rebuild or redeploy. The client-side catalog index and search work exactly as before. `/api/domain-graph` stays available to API and MCP users.
